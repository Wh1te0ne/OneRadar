# OneRadar V1 PRD（信息雷达与临时解析服务一期）

## 1. 产品定位

## 1.0 2026-06 产品方向重置

OneRadar 不再定位为内置阅读库、稍后读和个人知识库。新的核心定位是：

- 持续维护 RSS 信息源，缓存新闻条目，支持日报生成和外部调用。
- 提供每日新闻页面，作为用户每天查看 AI 汇总新闻的主入口。
- 提供临时链接分析能力：用户粘贴网页、微信公众号、Bilibili 等链接后，系统返回可复制的原文/正文、摘要和结构化结果，但默认不保存为阅读条目。
- 将同一套临时分析能力暴露为 API/MCP，供其他产品、Obsidian 工作流或 AI Agent 调用。

知识沉淀、长期笔记、阅读标注、收藏夹、文件夹和知识库组织不再由 OneRadar 承担，应交给 Obsidian 等外部笔记系统。

## 1.1 最新补充约束

以下约束优先于此前的泛化表述以及本文件中尚未清理完的历史 reader-first 章节：

- 一期正式化后支持轻量账号系统：用户名/邮箱 + 密码登录注册。它仍是私有部署产品，不做团队协作、公开注册运营、计费或复杂 SaaS 能力。
- 当前界面以全中文为主，多语言和英文支持后置。
- 不再提供 Inbox / 稍后阅读 / Library / 文件夹 / 收藏夹 / 阅读器 / 笔记 / 高亮作为主产品能力。
- 链接分析结果默认不持久保存为阅读条目；长期知识沉淀交给 Obsidian 等外部系统。
- 客户端必须支持浅色、深色、跟随系统三种主题模式，默认跟随系统。
- 模型 provider 配置必须保留，并作为日报生成、临时分析摘要、未来多平台分析的核心依赖。
- RSS 在当前阶段作为受控新闻发现与日报入口加入：用户手动维护 RSS 源，系统可缓存源更新，并每天默认 10:00 调用已配置大语言模型生成一份中文每日新闻。订阅源条目以本机数据库为准持续累积保存，刷新时不因 RSS 源只暴露最新若干条而删除旧记录，只有删除订阅源时才清理其缓存条目。日报候选内容取实际生成时刻往前 24 小时的 RSS 缓存条目。日报按日期永久保存，每天只保留一份当前版本；用户可手动重新生成并覆盖当天版本。日报结构必须 AI 优先：头条和头部新闻优先选择 AI，第一主题必须是 AI，AI 占比应高于其他主题，游戏新闻放在最后。RSS 条目不进入内部阅读库，不做已读/未读状态，点击直接打开原文链接。OneRadar 也通过内置 MCP 入口向 Hermes Agent 暴露指定时间窗口内的原始结构化新闻条目；这个入口只提供完整数据源和源状态，不负责生成播报文案。


OneRadar V1 不是“全网信息采集器”，也不再是内置阅读库或个人知识库，而是一个 **桌面优先、服务端驱动、自托管的信息雷达与临时内容解析服务**。

它的核心目标是：

- 持续收集用户维护的 RSS 信息源
- 每天生成和展示中文新闻简报
- 接收用户手动提供的链接，返回原文/正文、摘要和结构化分析结果
- 通过 API/MCP 让其他产品或 AI 调用新闻和链接分析能力

它更接近：

- Inoreader / Feedly 的自管 RSS 源和新闻流
- Google News / FT News Feed 的新闻简报与来源跳转
- 一个可被 Obsidian、Agent 或其他产品调用的内容解析接口

但第一阶段明确限制范围：

- **只对用户维护的 RSS 做持续收集**
- **不做通用自动采集平台**。RSS 的范围限定为用户手动维护订阅源、阅读更新、生成每日新闻；不会把 RSS 条目自动导入阅读库。播客页允许订阅播客 RSS，用于发现节目单集；不会自动下载或自动处理未加入稍后阅读的单集。
- **不做浏览器插件一键收藏**
- **不做多端同步优先**

临时链接分析入口由 **用户手动提供链接** 触发，包括：

- 文章网页链接
- Bilibili 视频链接
- 微信公众号、YouTube、抖音、小红书等后续平台链接

移动端补充：V1 可以提供手机版网页/PWA 作为同一服务的移动访问入口。移动端不引入专用后端、专用账号或第二套数据模型，应复用现有账号、服务器地址、RSS、日报、链接分析、API/MCP 和模型配置数据。

## 2. 一期目标

### 2.1 要解决的问题

当前用户获取和处理信息的方式通常是：

- RSS 源分散在不同工具里
- 每天新闻需要人工筛选
- 临时看到的网页、公众号、视频或社媒链接需要快速提取正文和总结
- 需要把结果交给 Obsidian、Agent 或其他产品继续使用

这些方式的问题是：

- 数据源和每日新闻入口分散
- 临时分析经常被迫先保存再处理
- RSS 与 AI Agent 之间缺少稳定、可审计的数据接口
- 模型配置分散，难以支撑日报和链接分析的统一摘要能力

OneRadar V1 要解决的是：

1. 用户维护 RSS 源后，系统持续刷新并缓存新闻条目
2. 用户每天可以看到按日期保存的中文每日新闻
3. 用户给一个链接后，可以得到原文/可见文本、摘要和结构化结果，但不进入内置阅读库
4. 其他产品、Obsidian 工作流或 AI Agent 可以通过 API/MCP 调用新闻和临时分析能力

### 2.2 一期成功标准

满足以下条件即可认为一期成立：

1. 用户可在桌面端维护 RSS 源并查看刷新结果
2. 服务端可按日期生成和保存每日新闻
3. 用户可提交临时链接并得到正文/可见文本、摘要和结构化结果
4. MCP 能向 Hermes 等 Agent 提供 RSS 来源状态和时间窗口新闻
5. 外部产品可用集成令牌调用临时分析 API
6. 模型 provider 配置可支撑日报和链接分析摘要
7. 服务端支持 Docker 部署

## 3. 非目标

OneRadar V1 明确不做：

- 内置阅读库、稍后读、笔记和知识库管理
- 浏览器插件收藏
- 邮件转发采集
- 批量网页抓取
- 推荐流和公共内容分发
- 独立 Android / iOS 原生客户端重写
- 复杂社交能力
- 重型 Agent 聊天产品
- 自动发现和批量抓取视频源

说明：

音视频和社媒平台能力不是一期的持续采集重点，而是临时链接分析适配器。第一阶段先把“RSS 持续收集 -> 日报 -> 临时链接分析 -> API/MCP 调用”闭环做稳。

## 4. 目标用户

一期先服务私有部署里的少量个人账号。默认既有数据归属 `whiteone` 账号；新增账号拥有独立的模型配置、RSS 源、日报、集成令牌和临时调用上下文。

画像：

- 有持续关注 RSS 信息源和 AI/科技新闻的习惯
- 经常需要把网页、公众号、视频或社媒链接快速转成可复制内容
- 更关心“能不能快速分析并交给 Obsidian 或 Agent 使用”
- 能接受自托管服务端
- 使用 Windows 桌面作为主阅读终端
- 对信息组织能力的需求高于“采集入口数量”

## 5. 核心使用场景

### 5.1 手动入库

用户在桌面端粘贴一个链接，系统：

- 校验 URL
- 根据链接类型进入文章或视频处理流程
- 抓取基础信息
- 生成一份可阅读、可检索的内容条目
- 存入个人资料库

### 5.2 Bilibili 视频转写分析

用户粘贴一个 Bilibili 视频链接，系统：

- 获取标题、UP 主、封面、时长等基础信息
- 优先获取现成字幕
- 对需要登录态的字幕，桌面端可通过显式本机授权动作导入 Bilibili Cookie 辅助抓取
- 无可用字幕时抽取音轨并转写
- 保留时间戳
- 生成摘要、大纲、关键片段
- 将结果以“可阅读条目”形式入库

### 5.2.1 播客发现与单集入库

用户可在播客页搜索节目并订阅 RSS。系统：

- 使用 Apple iTunes Search API 查找播客节目，并读取结果中的 RSS `feedUrl`
- 保存用户已订阅的播客源
- 按发布时间展示所有已订阅节目的 episode 流
- 不因订阅而自动下载音频或触发模型处理
- 仅在用户对某一集点击“加入稍后阅读”后创建 OneRadar 内容条目
- 对已加入的单集做 UID 去重，避免重复下载和重复解析
- 为已加入单集持久保存音频 artifact，以便未来更换模型后重新解析

### 5.3 Inbox 收件箱

新导入的内容默认先进入 Inbox，用户后续可以：

- 保持在收件箱待读
- 移动到某个文件夹
- 标记为已归档

### 5.4 稍后读

用户将内容先保存，稍后在桌面端打开：

- 阅读清洗后的正文或转写内容
- 查看原始链接
- 查看元数据
- 查看 AI 生成的简要摘要或大纲

### 5.5 精读与标注

用户在阅读过程中可以：

- 高亮段落
- 添加笔记
- 加标签
- 放入收藏夹/专题

### 5.6 回查与再利用

用户以后可通过：

- 关键词
- 标题
- 标签
- 收藏夹

快速找到过去保存过的内容。

## 6. 一期功能范围

## 6.1 必做功能

### 内容导入

- 手动粘贴链接导入
- 导入后创建内容条目
- 去重判断（同一规范化 URL 不重复建条目）

### 内容解析

- 获取标题、站点名、作者、发布时间（尽力而为）
- 文章链接：抓取原始 HTML、提取可阅读正文、保存阅读快照
- Bilibili 链接：拉取字幕或抽音轨转写，并保存带时间戳文本
- 播客单集：下载 RSS enclosure 音频并持久保存，再进入转写和摘要流程

### 阅读体验

- Inbox 收件箱
- 文件夹视图
- 内容列表
- 内容详情阅读页
- 原文链接跳转
- 阅读进度记录
- 基本排版设置（字体大小、行宽、主题）
- 主题模式：浅色 / 深色 / 跟随系统

### 知识沉淀

- 高亮
- 笔记
- 标签
- 文件夹
- 收藏夹/专题集

### 播客

- 独立播客页
- Apple iTunes Search API 搜索节目
- 订阅 / 取消订阅播客 RSS
- 已订阅节目按 episode 发布时间倒序聚合显示
- 单集手动加入稍后阅读
- 已加入单集去重，返回已有 UID
- 音频仅在单集加入稍后阅读后下载，删除条目时清理对应音频 artifact

### 检索

- 标题搜索
- 正文关键词搜索
- 标签筛选
- 收藏夹筛选

### AI 辅助

- 一句话摘要
- 短摘要
- 结构化大纲
- 视频重点片段/时间戳锚点

对于视频内容：

- 优先使用现成字幕
- 无字幕时进入音轨转写
- 输出结果必须保留时间戳，方便回跳

AI 结果是增强项，但不应该阻塞基础阅读。

### 系统能力

- 单用户免登录使用
- 服务端连接与配置管理
- 模型 provider 管理
- Docker 部署
- 基础任务状态与失败重试

模型 provider 管理至少应支持：

- 预设常见 provider，如豆包、DeepSeek
- 用户自行添加自定义 provider
- 配置 base URL、API Key、模型列表或默认模型
- 区分转写模型、摘要模型、嵌入模型
- 测试连通性与当前模型切换；同一能力只保留一个当前模型

## 6.2 可选但不强求

- 页面封面抓取
- 阅读时间估算
- 导入备注
- 归档状态

## 6.3 暂缓功能

- 内置稍后读/阅读库
- 浏览器插件
- 多语言界面（后置阶段，当前以全中文为主）
- 邮件导入
- 本地文件导入
- PDF 阅读
- 语义搜索
- 多用户权限系统

## 7. 产品结构

一期只有两个主要产品面：

### 7.1 服务端

职责：

- 提供 API
- 执行抓取和解析
- 执行字幕获取、音轨抽取和转写
- 生成 AI 摘要
- 存储原始与清洗内容
- 提供搜索与组织能力
- 提供管理配置界面或最小管理接口

部署要求：

- 支持 Docker Compose
- 支持本地目录持久化
- 配置尽量集中在 `.env`

### 7.2 桌面端

职责：

- 单用户免登录进入
- 手动添加链接
- 浏览内容库
- 阅读条目
- 标注、笔记、标签、收藏夹
- 搜索与筛选

平台要求：

- 一期先做 Windows 桌面版
- UI 以阅读体验优先，不追求复杂编辑器

## 9. 用户流程

## 9.1 链接入库流程

1. 用户在桌面端粘贴链接
2. 客户端请求服务端创建导入任务
3. 服务端规范化 URL 并检查是否已存在
4. 服务端识别链接类型
5. 文章链接进入正文提取流程
6. 视频链接进入字幕/转写流程
7. 生成统一的可阅读内容对象
8. 异步生成摘要和大纲
9. 写入全文索引
10. 客户端展示可阅读结果

## 9.2 阅读与沉淀流程

1. 用户打开条目
2. 查看摘要或直接阅读正文/转写内容
3. 对关键段落进行高亮
4. 为条目添加笔记、标签、收藏夹
5. 后续通过搜索再次回到该条目

---

## 10. 信息输出标准

每条内容最终应统一为一个条目对象，至少包括：

- 基础信息：标题、站点、作者、发布时间、原始 URL
- 原始材料：HTML 快照或字幕/转写结果
- 阅读材料：清洗后正文，或带时间戳的转写文本
- AI 结果：一句话摘要、短摘要、结构化大纲
- 用户数据：高亮、笔记、标签、收藏夹、阅读状态
- 检索数据：全文索引

## 11. 非功能需求

### 11.1 性能

- 单篇常规文章解析在可接受时间内完成
- 单个视频转写允许异步处理
- 阅读详情页首屏优先展示标题、摘要和正文前部
- 搜索尽量保持秒级返回

### 11.2 稳定性

- 抓取失败可重试
- AI 失败不影响基础阅读
- 转写失败应允许单独重跑
- 解析流程应分步骤可观测

### 11.3 安全性

- 所有 API Key 仅保存在服务端
- 导入链接需做 SSRF 风险控制
- 外部媒体下载与转写流程需隔离执行
- 文件存储默认私有
- 日志避免记录敏感 Cookie 和密钥

### 11.4 可维护性

- 解析器、AI、搜索分层解耦
- 内容源适配器可扩展
- 模型 provider 适配器可扩展
- 客户端与服务端接口稳定

### 11.5 本地化与主题

- 一期界面文案默认中文
- 英文和多语言支持后置
- 客户端支持浅色、深色、跟随系统三种主题模式
- 默认主题模式为跟随系统

## 12. 技术方向建议

## 12.1 服务端

推荐：

- Python + FastAPI
- PostgreSQL
- Redis
- Worker 队列

原因：

- 网页抓取、正文提取、音视频处理、AI 调用生态成熟
- 容易快速验证解析与阅读闭环
- Docker 化成本低

## 12.2 桌面端

推荐：

- Tauri + React

原因：

- 一期明确是桌面端
- 比 Electron 更轻
- 前后端边界清晰
- Web UI 可以最大化复用到未来的移动端/PWA

## 12.3 正文提取

建议优先组合：

- Readability
- Trafilatura
- 自定义清洗规则

目标是优先得到“稳定可读正文”，不是追求全站覆盖率。

## 12.4 视频处理

建议优先策略：

- 现成字幕
- 自动字幕
- 音轨抽取 + ASR

目标是优先拿到可追溯文本，而不是一开始追求最复杂的多模态理解。

## 12.5 搜索

一期建议优先：

- PostgreSQL 全文检索

语义搜索可以推迟到后续版本。

## 12.6 AI 能力

一期建议只做：

- 标题/正文/转写摘要
- 结构化大纲
- 转写模型与摘要模型分离配置
- 多 provider 管理

## 16. 与原 PRD 相比的关键修订

需要从原文档中明确改掉的地方：

1. 产品定义从“AI 内容解析器”改为“阅读库/知识库产品”
2. 一期输入从“多来源采集”改为“用户手动提供链接”
3. 一期重点从“自动采集”改为“手动链接输入后的阅读体验与知识沉淀”
4. 一期平台从“多端访问”收敛为“服务端 + Windows 桌面端”
5. 一期搜索先做关键词/全文，不优先做语义搜索
6. 一期不做 RSS、不做浏览器插件、不做自动采集
7. 一期支持手动输入的 Bilibili 视频转写与分析
8. 一期支持预设 provider 与自定义模型 provider 管理

## 17. 关于客户端形态的建议

建议采用 **Web 核心 + 桌面壳** 的路线，而不是一开始就分别做桌面原生和手机原生。

原因：

- 阅读、列表、搜索、设置这些界面本质上都适合 Web UI
- 一期可以更快落地 Windows 桌面端
- 未来做手机端时，业务逻辑、API、设计系统、绝大部分页面结构都能复用
- 即使未来真的做手机原生，也不会是“全部重写”，而更接近“复用服务端和前端架构，重做部分交互层”

真正会重做的，主要是：

- 导航结构
- 手势交互
- 选中文本与高亮体验
- 移动端阅读排版细节

不会重做的，通常是：

- 服务端
- 数据模型
- API
- 抓取/转写/摘要流水线
- 搜索逻辑
- 大量 UI 文案、信息架构和状态机
